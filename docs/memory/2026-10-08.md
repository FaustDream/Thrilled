## 壁纸自适应裁剪 + 历史管理 + 去重（用户反馈）

**先纠正一处前提**：反馈说「壁纸无法自适应屏幕、只显示一部分」，但 `.wall-img` 早已是 `object-fit:cover`——等比缩放填满、不变形、无黑边都已满足，**「只显示一部分」正是 cover 的必然结果**（不变形就必须裁切）。真正的缺口是**裁剪位置固定居中**，人像 / 地平线偏侧的图会被切掉主体。另外澄清两点：Thrilled 是 Chrome 新标签页扩展，没有「设备壁纸」层，壁纸只在页面内渲染；取的是**视口**参数而非 `screen.*`（多屏或缩放下 `screen.width` 是主屏物理分辨率，与页面视口对不上）。

**一、裁剪焦点算法**（新增 `src/core/wallpaper-focus.ts`）

纯函数与浏览器采样分两层，前者可直接单测：

- `sampleLuma(dataUrl)`：`<img>` 解码 → 降采样到 256px 宽 → 画到 canvas → 转灰度 `Float32Array`。壁纸是 base64 dataURL，同源不污染 canvas，`getImageData` 安全。
- `focusOffset(lum, gw, gh, screenRatio)`：比值判断可移动轴（图比屏宽裁左右、图比屏高裁上下、相等则不裁），沿该轴 **32 步滑窗**搜索。每个窗口算三个归一化分数加权：
  - **Sobel 边缘能量**（×0.7）——主体 / 纹理密度，主判据
  - **中心先验**（×0.2）——距图心距离，避免无谓偏移
  - **明度方差**（×0.4 缩放后 ×0.1）——排除纯色天空 / 地面
  - 返回 `object-position` 百分比（0% 贴左/上、100% 贴右/下，与 CSS 语义一致）
- `computeWallFocus(dataUrl, ratio)`：采样 + 评分一步到位；解码失败退回居中但仍记下比例，避免反复重试。

**踩坑**：测试合成图最初用 1px 棋盘，Sobel 在中心点对称抵消、梯度恒为 0，算法退化成只看方差。改用 3px 块状棋盘（真照片不会有这种病态图案），并在测试里留注释。

**二、应用与重算**（`App.tsx` / `types` / `defaults` / `guards` / `store`）

- `settings.wallFocus = { x, y, ratio }`，`ratio` 记录算它时的视口宽高比
- 新增 `vpRatio` state：在既有 `fit()` 里更新，**变化超过 1% 才 setState**，避免 resize 抖动触发无谓渲染
- effect 判据 = `换壁纸（focusFor.current !== ref）|| ratio 为 0 || 比例变化 ≥ 3%`
- 渲染：`<img className="wall-img" style={{ objectPosition: '${x}% ${y}%' }}>`

**修掉的缺陷 1**：初版判据只比视口比例，换壁纸时因比例未变而沿用上一张的焦点（实测换图后仍是 56%）。补上壁纸引用比对后，同一张测试图从 56% 修正为 94%。

**三、历史壁纸**（`wallpaper.ts` / `panels.tsx` / `prototype.css`）

- `BgData` 补 `src` / `from` / `at`；`normBg` 在读取时给早期记录补默认值（`from: '早前添加'`、`at: 0`）
- `listWallpapers()`：`getAllKeys` + `getAll`，按 `at` 倒序，IndexedDB 原生能力，不建索引
- 面板加 `.wp-history` 横向缩略图带：当前项主题色描边、悬停显示「来源 · 日期」、点击直接 `setWallpaperRef` 切换
- `pruneWallpapers()` 按 `WALLPAPER_HISTORY_LIMIT = 12` 淘汰

**四、去重**（`wallpaper.ts` / `panels.tsx`）

- `wallpaperRefOf(seed)`：`crypto.subtle.digest('SHA-256')` 取前 16 位十六进制。种子规则 `url:<源地址>` / `data:<dataURL>`（带前缀避免碰撞）。无 SubtleCrypto 时退回时间戳（不去重但可用）。
- `findWallpaperBySource(src)`：应用前先查，命中就 `move({ stage: 2, reused: true })` 直接跳到应用阶段，**整段下载省掉**；浮层文案「本地已有同一张，直接复用记录应用，无需重新下载」。
- `storeRemoteWallpaper(src, dataUrl, from)` 内部也查一次（并发兜底）。

**修掉的缺陷 2**：淘汰只豁免「刚入库的那张」。用户从历史切回旧图后再上传，那张**正在使用**的旧图会被当成溢出历史删掉。补 `markActiveWallpaper(ref)` 模块状态，豁免名单 = 刚入库的 + 当前使用的。同步点放在 **store 的 `useApp.subscribe`** 而不是组件 effect——hydrate / 云端恢复 / 重置 / 历史切换都会改写 `wallpaperRef`，订阅能覆盖全部来源且不依赖挂载时序（初版写在 App 的 effect 里，被 hydrate 覆盖后失效）。

**验证**（Chrome，dev server + 临时 mock 提供 Wallhaven 协议与主体偏右的 SVG 测试图，验证后已删除）

| 项 | 结果 |

**关键设计：两类公式并存**。前六项是「玻璃底色」，沿用 `1 − 0.55×值` 保留可读下限——老持久化数据（如 `card: 0.6` → alpha 0.67）外观**零跳变**；后六项是「元素显隐强度」，用 `1 − 值` 才能「让它淡入背景」直到消失。两者靠 `GLASS_FADED_KEYS` 区分，CSS 侧无感知（`--ga-*` 存的都是最终 alpha）。

**收敛技巧**：边框 / 悬停高亮不需要逐条改选择器——由 JS 把皮肤令牌 `--line` / `--menu-hover` 用 `color-mix` 派生（`fadeToken`），**可见度满格时直接 return 不覆盖**，保证默认外观与旧版逐像素一致；CSS 里所有 `var(--line)` 自动跟随。顺带把硬编码的 `.sp-row:hover{background:#f4f6fa}` 改成 `var(--menu-hover)` 才能被强度控制。

**图标分层**：`TileGlyph` 的字形包了一层 `<span class="glyph">`。原来「容器」与「图形」是同一个元素（`.v-icon` / `.dock-icon`），无法分别调；现在容器底色走 `--ga-tile`，图形走 `--ga-glyph`（Dock 内覆写为 `--ga-dockIcon`）。

**三、毛玻璃与透明度解耦**

- `settings.blur` 独立字段（`BlurKey` = card/tile/dock/search/panel/menu，与有玻璃底色的六个透明度项配对），`BlurSettings = Record<BlurKey, number>`，取值 0–20px

- 面板拆成三张卡：**透明度**（全局 + 12 项）、**毛玻璃模糊**（6 项，0–20px）、**壁纸与文字**（遮罩 + 字体颜色）

## 模式胶囊收起态图标未居中（用户反馈）

- 去掉 `.mode-pill` 的 `gap:6px`
- 间隔改由 `.pill-opts` 的 `margin-left` 承担：收起 0、`hover`/`.open` 时 6px，并加入过渡属性列表（`margin-left .22s var(--ease)`），展开动画不变

## 在线壁纸应用的分阶段交互反馈（用户需求）

**问题**：点壁纸缩略图后，从点击到主页出现新背景之间有三段耗时（下载原图 → 校验写入 IndexedDB → 写设置并渲染），原先唯一的进度信号是 `.wall-thumb.sel` 的 2px 描边——几乎不可见。Wallhaven 原图常有数 MB，慢源下用户会把等待当成卡死或未响应。

**阶段划分**（与实际代码路径一一对应，非编造）

| 阶段 | 文案 | 实际做的事 | 耗时来源 |
| --- | --- | --- | --- |
| 0 | 正在下载壁纸 | `fetchDataUrl` 网络请求 + 转 base64 | 网络，慢源可达数十秒 |
| 1 | 正在处理图片 | 20MB 体积校验 + `idbSet` 写 IndexedDB | 几 MB 字符串处理 + IDB 写 |
| 2 | 即将应用 | `setWallpaperRef` → 主页读回 → 渲染 | 通常很快，但需要可读的落点 |

**改动**

1. `core/fetch-proxy.ts` — `fetchDataUrl(url, onProgress?)` 新增可选进度回调：
   - 直连路径：新增 `readBlobWithProgress`，用 `res.body.getReader()` 逐块累计 `loaded`，`total` 取 `Content-Length`，每块回调一次
   - SW 代理路径：一次性返回字符串，中间进度不可知 → 回调 `onProgress(0, 0)`，由 UI 走不确定态
   - 响应不支持流时（`res.body === undefined`）退化为一次性 `res.blob()`，回调 `(size, size)`
   - **类型坑**：`reader.read()` 的 `value` 是 `Uint8Array<ArrayBufferLike>`，直接 `push` 进 `BlobPart[]` 会触发 TS2322（`wallsource.ts` 已踩过同一个坑）。解法是每块拷进独立 `ArrayBuffer` 段：`const seg = new Uint8Array(value.byteLength); seg.set(value); parts.push(seg.buffer)`
2. `core/wallpaper.ts` — `saveRemoteWallpaper` 拆出 `storeRemoteWallpaper(dataUrl)`（只做体积校验 + 入库）。原函数把下载与入库合在一起，UI 无法在两步之间切阶段；`fetchDataUrl` 本身已在 fetch-proxy 暴露，`WallBrowser` 直接串两步即可。原函数无其他调用方，已删除，不留兼容层

## 壁纸「已应用但没有壁纸」（用户反馈）

**现象**：从 Wallhaven 点缩略图设为壁纸，面板显示「自定义壁纸 · 6.1 MB」、缩略图正常，toast 也提示已应用，但主界面没有任何壁纸。

**根因**：**Blink/Chromium 对单条 CSS 声明（自定义属性）的值有 200 万字符硬上限，超出后 `setProperty` 静默失效**——不抛异常、值被丢弃、旧值原样保留。

原实现把整个 dataURL 塞进 CSS 变量（`App.tsx` effect：`rt.setProperty('--wallpaper', 'url("${data}")')` → `prototype.css` `.wall-layer{background-image:var(--wallpaper),…}`）。base64 比原图大 33%，6.1MB 图对应约 830 万字符，远超上限，于是 `--wallpaper` 始终停在 `none`。而面板缩略图走 `<img src={data}>`，不受该限制，所以"看起来成功、实际没生效"。本地压缩后的壁纸若小于约 1.5MB 则恰好不触发，这也是长期未暴露的原因。

**实测阈值**（Chromium，`.wall-layer` 同一元素上逐档探测）：

| 字符数 | 结果 |
| --- | --- |
| 1,000 / 100,000 / 500,000 / 1,000,000 / 2,000,000 | 生效 |
| 3,000,000 / 4,296,000 | **静默丢弃**（`getPropertyValue` 仍返回旧值） |

**修复**（`App.tsx` / `prototype.css`）：

1. 图片壁纸改由 `<img class="wall-img" src={customWall.data} />` 承载（`.wall-img` 用 `position:absolute;inset:0;width/height:100%;object-fit:cover` 对应原 `background-size:cover`）；视频壁纸的 `<video class="wall-video">` 路径不变。
2. 删除写`setProperty('--wallpaper', …)` 的整个 effect。
3. `.wall-layer` 只留 `position:fixed;inset:0;z-index:0` + `filter:blur(var(--wp-blur))`；细斜纹纹理原本是 `background-image` 的第二层（画在壁纸**之上**），换成 `<img>` 后会被图片压住，故移到 `.wall-layer::after` 独立叠加层。
4. 清理死代码：`#stage::before` / `#stage::after` 的壁纸 / 遮罩规则早已被第 18 节的 `#stage::before,#stage::after{content:none}` 废掉，其中还残留 `var(--wallpaper)` 引用，一并删除。

**验证**：`playwright-cli` 起 dev server 端到端——IDB 写入 4.29MB dataURL + `settings.wallpaperRef` 指向 → 重载 → `.wall-img` 存在且 `naturalWidth/Height = 2560x1440`、壁纸铺满全窗口（截图确认）、遮罩与模糊正常；`setWallpaperRef(null)` 后 `<img>`/`<video>` 均卸载、回退遮罩底色。`vitest run` 56 例通过，`node scripts/build.mjs` 成功。

**需求原话**：重新改造设置界面的整体布局，参考个性化界面 UI 的分布方式来组织模块与控件；明确功能分区、模块层级、主次排布规则；体现个性化风格（模块划分、信息密度、导航方式、交互区域位置分配）；保持原有功能完整，优化空间利用与视觉层次。

**改前状态**：设置抽屉是**一列长滚动**——8 个裸标题（`.sec-title`，无卡片边界）串起引擎、搜索框、问候、打开方式、数据与备份、云端、关于、快捷键；「数据与备份」是 9 个按钮的按钮墙（主次不分）；打开方式用三条各带开关的行表达互斥选项（三行都能「开」）；「上传到云端」在数据组与云端组各出现一次。

**一、功能分区（5 个页签，顺序 = 使用频率 × 风险）**

| 页签 | 卡片（层级：上=主，下=次） | 内容 |
| --- | --- | --- |
| 搜索 | 搜索引擎 → 搜索框 | 引擎清单（拖拽 / 启用 / 隐藏 / 添加自定义 / 弹窗管理）、四个搜索框行为开关 |
| 通用 | 打开方式 → 每日问候 | 打开方式互斥单选、昵称 |
| 数据 | 备份与迁移 → 重置与清理（标红） | 备份 / 恢复默认 / 导出 / 导入布局 / 导入收藏夹 / 恢复快照；清除本地数据 / 一键重置 |
| 云端 | 云端同步（单卡） | 服务器地址 / 令牌 / 保存 / 上传 / 恢复 |
| 关于 | 关于 → 快捷键 | 版本、更新记录 / 关于我们、快捷键表 |

引擎下拉里的「管理搜索引擎」（`engine-manage`）落在**首个页签首张卡片**上，从搜索框进设置的路径不变。

**二、主次内容排布规则**（三条，落地在代码注释里）

1. **分区按频率**：高频（搜索）在前，只读与危险（关于 / 数据）在后。
2. **卡片内主次**：可即时生效的开关与单选项常驻主体；低频动作（导出 / 导入 / 快照 / 收藏夹）从小号实底降为第二行的 `btn sm ghost`；说明文案全部收进标题右侧 ⓘ（信息密度：默认只有控件，解释按需展开）。
3. **危险隔离**：覆盖 / 删除类操作单独成「重置与清理」卡，红色描边 + 红色标题（新增 `.sec-card.danger`），不与常规操作同排一列按钮。

**三、导航与交互区域**

- 顶部页签改用新增的共用 `DrawerTabs`（个性化与设置同一套页签语言，`PANEL_TABS` 顺带由 `readonly (readonly [string])[]` 简化为 `string[]`）；正文区与个性化一致为「页签 → 卡片」两级。

## 类型错误清零（用户要求）

**问题**：`src/core/wallsource.ts` 9 处 `tsc` 报错（上一轮哲风适配器带入，阻塞 `pnpm typecheck` 与 `pnpm prepack`）。

| 报错 | 位置 | 原因与改法 |
| --- | --- | --- |
| `TS2322` ×2 | `zfEncrypt` / `zfDecrypt` 里的 `iv` | `zfKeyIv` 的返回类型写成 `iv: Uint8Array`（默认 `ArrayBufferLike`），与 WebCrypto 的 `BufferSource`（`ArrayBufferView<ArrayBuffer>`）不兼容 → 显式声明 `Uint8Array<ArrayBuffer>`，并补一行说明 |
| `TS18046` ×6 | `parseZhefengList` 里的 `body['list' / 'total' / 'pages']` | `let body: unknown` 无法索引 → 改为 `Record<string, unknown>`（与文件内 `itemOf` 的既有约定一致） |
| `TS7006` ×1 | `rows.map((x) => …)` | `body` 报错导致 `rows` 收窄失败、`x` 隐式 `any` → 显式声明 `const rows: unknown[]`，回调参数随之为 `unknown` |

**验证**：`pnpm typecheck` exit 0（9 → 0）；`pnpm test` 73 例通过；`eslint src/core/wallsource.ts` 仅剩既存 1 条 `no-control-regex`（`zfDecrypt` 中匹配 NUL 的正则，属有意匹配，未改）。

**纯类型改动核对**：`node scripts/build.mjs --prod` 重新构建后与已发布 `releases/thrilled-4.4.zip` 逐文件 SHA-256 比对 **9/9 一致**（`background.js` / `assets/*` / `manifest.json` / `index.html` / `icons/*`）→ 运行时零变化，已发布产物无需重发。
